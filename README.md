# dc-mac-kit — INPAS DualConnector на macOS (Apple Silicon)

Комплект для запуска **DC Linux Service** (INPAS DualConnector 2.0) на маке с Apple Silicon: установщик, службы launchd, диагностика, тестовый клиент HTTP API и два моста. **paxbridge** подключает терминалы PAX по USB без драйвера ядра, **btbridge** — терминалы по Bluetooth в обход последовательного порта macOS.

Официально вендор macOS не поддерживает: DC — Java-приложение, но в его коде есть несколько мест, где ветки для macOS просто нет. Комплект обходит их снаружи — параметрами JVM, порядком classpath, раскладкой файлов — и **не изменяет ни одного файла дистрибутива**.

> **Неофициальный проект.** Не связан с ООО «Лаборатория платёжных решений» (INPAS), PAX Technology и их партнёрами и ими не поддерживается. Дистрибутив DC в комплект не входит — его нужно получить у поставщика. Названия продуктов принадлежат их правообладателям. Сведения о внутреннем устройстве DC получены анализом байт-кода ради совместимости; код вендора здесь не распространяется.

## Как это устроено

```
                                   ┌──TCP──────────────────────────────▶ терминал в сети          (Б)
                                   ├──TCP──▶ paxbridge ──USB (ttyPos)──▶ PAX в USB-режиме        (В)
кассовое ПО ──HTTP──▶ DC Service ──┤        127.0.0.1:27016
               :9015   (Java)      ├──TCP──▶ btbridge ──Bluetooth RFCOMM▶ терминал по Bluetooth   (Д)
                                   │        127.0.0.1:27017
                                   └──serial──▶ /dev/cu.* ─────────────▶ USB-CDC, COM, Bluetooth  (А, Г)
```

Кассовое ПО говорит с DC по HTTP — XML или JSON. DC держит связь с терминалом по протоколу SA одним из пяти способов:

| | Канал | Что нужно на маке |
|---|---|---|
| **А** | USB-CDC или RS-232: терминал виден как `/dev/cu.*` | jssc с нативной библиотекой под arm64 |
| **Б** | Ethernet / Wi-Fi: терминал слушает TCP-порт | ничего сверх DC |
| **В** | USB в «стандартном» режиме PAX (ttyPOS): COM-порта нет | мост `paxbridge` — userspace-замена модулю ядра `ttyPos` |
| **Г** | Bluetooth (профиль SPP): после сопряжения терминал виден как `/dev/cu.<имя>` | то же, что для А, но на macOS 26 этот порт ненадёжен (см. вариант Г) |
| **Д** | Bluetooth (профиль SPP) без `/dev/cu.*` | мост `btbridge` — сам открывает канал RFCOMM |

Установщик ставит DC и paxbridge как службы launchd: они стартуют при загрузке и перезапускаются при падении. btbridge — агент launchd в сессии пользователя: доступ к Bluetooth macOS выдаёт приложениям пользователя.

## Совместимость и что проверено

| | |
|---|---|
| macOS | 26 (Tahoe), Apple Silicon |
| DC Linux Service | 2.0.17.7; 2.1.0.15 — варианты Г и Д, тест связи |
| Java | 21 arm64 (подойдёт любая 11+) |
| Терминал | PAX D230 (Prolin, USB `2FB8:1101`, `bcdDevice 0x0300`) |

| Канал | Результат |
|---|---|
| **Б**, сеть | тест связи и оплата прошли |
| **В**, USB через paxbridge | тест связи, оплата и отмена прошли; мост работает службой launchd |
| **Г**, Bluetooth | на DC 2.0.17.7 тест связи и оплата прошли; на 2.1.0.15 тест связи проходит, но связь рвётся после перезапуска DC (см. вариант Г) |
| **Д**, Bluetooth через btbridge | DC 2.1.0.15: тест связи 15 из 15, в том числе после перезапусков DC, моста и перезагрузки терминала; оплата не проверялась |
| **А**, USB-CDC / COM | тот же путь через последовательный порт и jssc работает по Bluetooth (Г); с терминалом по USB-CDC или RS-232 **не проверялся** |

Маки на Intel не проверялись. Препятствий нет — jssc содержит сборку `osx_64`, установщик выбирает её автоматически, — но и подтверждения тоже нет.

## Зависимости

**Обязательно:**

- macOS на Apple Silicon.
- Дистрибутив **DC Linux Service 2.0.17.7** — получается у поставщика INPAS. Из него нужен каталог `files/` (`dcservice.jar` и утилиты).
- **Java 11+, сборка arm64.** Рекомендуется системный JDK, например Temurin: `brew install --cask temurin@17`. Рантайм внутри IDE (JetBrains `jbr-*` в `~/Library`) работает, но пропадёт при обновлении IDE, и служба встанет — установщик об этом предупреждает.
- Права `sudo`: установка пишет в `/opt`, `/Library/LaunchDaemons` и `/etc`.
- Доступ в интернет при установке — за jssc (см. ниже). Без сети: `JSSC_JAR_PATH=/путь/jssc-2.10.4.jar ./install.sh`.

**Ставится автоматически:**

- **jssc 2.10.4** (`io.github.java-native:jssc`, LGPL-3.0) — скачивается с Maven Central в `vendor/`. Нужен для канала А.
- **pyusb** (BSD-3-Clause) — в отдельное виртуальное окружение моста. Нужен для канала В.

**Нужно поставить самому для канала В:**

- **libusb**: `brew install libusb`.
- **python3** — входит в Xcode Command Line Tools: `xcode-select --install`.

**Нужно поставить самому для канала Д:**

- **swiftc** — тоже из Xcode Command Line Tools: установщик собирает мост из `btbridge.swift` на месте.

Остальное — штатные утилиты macOS: `curl`, `iconv`, `unzip`, `plutil`, `launchctl`, `ioreg`, `nc`, `xmllint`.

## Установка

Положите комплект **внутрь распакованного дистрибутива**, рядом с `files/`, `Scheme/`, `Documents/`:

```bash
cd "DualConnector Service Linux 2.0.17.7"
git clone https://github.com/skhrvg/dc-mac-kit.git macos-kit
cd macos-kit
./install.sh
```

Если комплект лежит в другом месте, укажите дистрибутив явно:

```bash
DC_DIST="/path/to/DualConnector Service Linux 2.0.17.7" ./install.sh
```

### Что делает install.sh

1. Проверяет Java: версию, архитектуру, расположение.
2. Скачивает jssc (или берёт из `vendor/` / `JSSC_JAR_PATH`).
3. Раскладывает всё в `/opt/dcservice`, достаёт из jssc нативную библиотеку под вашу архитектуру.
4. Создаёт `connector.xml` из шаблона — **только если его ещё нет**, существующий не трогает.
5. Кладёт симлинки `/etc/connector.xml` и `/etc/dcposgui.xml` на файлы в `/opt/dcservice/service/config` (почему именно `/etc` — в разделе «Механика»).
6. Ставит мост paxbridge: виртуальное окружение с pyusb, находит libusb и прописывает путь к нему явно.
7. Если с маком сопряжён Bluetooth-терминал (или задан `BT_DEVICE`), собирает мост btbridge в `BTBridge.app` и ставит LaunchAgent пользователя.
8. Генерирует обёртку запуска, утилиту `dcctl` и два LaunchDaemon, выставляет права.
9. Проверяет, что нативные части jssc и jSerialComm грузятся.
10. Поднимает мосты, затем DC. Если `connector.xml` только что создан из шаблона, DC не запускает и просит сначала его отредактировать.

Повторный запуск безопасен: конфиг сохраняется, jssc не перекачивается, службы перезапускаются. Так же обновляется комплект и меняется Java.

### Переменные окружения

| Переменная | По умолчанию | |
|---|---|---|
| `PREFIX` | `/opt/dcservice` | куда ставить |
| `RUN_USER` | текущий пользователь | от чьего имени работают службы |
| `DC_DIST` | каталог над комплектом | где лежит дистрибутив DC |
| `JSSC_VERSION` | `2.10.4` | версия jssc |
| `JSSC_JAR_PATH` | — | взять jssc из файла вместо скачивания |
| `BRIDGE_PORT` | `27016` | порт моста paxbridge |
| `BT_DEVICE` | единственный сопряжённый терминал с последовательным портом | терминал для btbridge: имя или адрес (`a0-44-b7-…`) |
| `BT_PORT` | `27017` | порт моста btbridge |

### Что получается

```
/opt/dcservice/
├── dcservice.jar               из дистрибутива, без изменений
├── lib/jssc-2.10.4.jar         перекрывает встроенный jssc 2.9.2
├── native/libjssc.dylib        нативная часть jssc под вашу архитектуру
├── bin/dcservice-run.sh        запуск DC со всеми нужными параметрами JVM
├── bin/dcctl                   управление
├── bridge/paxbridge.py         мост USB для PAX
├── bridge/.venv/               python + pyusb для моста
├── btbridge/BTBridge.app       мост Bluetooth (собирается из btbridge.swift)
├── tools/                      утилиты дистрибутива (dcconsole, dcposgui, …) и проверки
└── service/
    ├── config/connector.xml    настройки DC; /etc/connector.xml ссылается сюда
    ├── config/dcposgui.xml     настройки окна кассира; /etc/dcposgui.xml ссылается сюда
    └── log/                    Connector*.log, launchd.*.log, paxbridge.log, btbridge.log
```

| Задание launchd | Что делает |
|---|---|
| `ru.inpas.dualconnector` | DC Service, HTTP на порту `SERVERPORT` (9015) |
| `ru.inpas.paxbridge` | мост USB, `127.0.0.1:27016` |
| `ru.inpas.btbridge` | мост Bluetooth, `127.0.0.1:27017` |

Первые два — `/Library/LaunchDaemons`, `RunAtLoad` и `KeepAlive`, работают от `RUN_USER`, а не от root: на macOS `/dev/cu.*` и USB-устройства vendor-класса доступны обычному пользователю. Мост Bluetooth — LaunchAgent в `~/Library/LaunchAgents` пользователя `RUN_USER` и работает, пока тот вошёл в систему (см. «Мост btbridge»).

Для удобства добавьте `dcctl` в `PATH`:

```bash
sudo ln -sf /opt/dcservice/bin/dcctl /usr/local/bin/dcctl
```

### Удаление

```bash
./uninstall.sh            # службы и программы; конфиг и логи в /opt/dcservice/service остаются
./uninstall.sh --purge    # всё, включая конфиг и логи
```

## Подключение терминала

Конфиг — `/opt/dcservice/service/config/connector.xml`, открыть в редакторе: `sudo dcctl config`. Оставьте **ровно один** вариант подключения: два тега `<CONNECTION_TYPE>` в файле — и какой из них победит, не определено.

**А. USB-CDC или COM**

```xml
<CONNECTION_TYPE>COM</CONNECTION_TYPE>
<CONNECTION_PORT>/dev/cu.usbmodemXXXX</CONNECTION_PORT>
<CONNECTION_BAUDRATE>115200</CONNECTION_BAUDRATE>
<AUTO_SEARCH>OFF</AUTO_SEARCH>
<ADVANCED_AUTO_SEARCH>OFF</ADVANCED_AUTO_SEARCH>
```

Порт — `dcctl ports`. Берите вариант `cu.*`, а не `tty.*`: `tty.*` блокируется при открытии, пока нет сигнала DCD. `AUTO_SEARCH` пропишите явно: по умолчанию он **включён**, а на маке не работает.

**Б. Ethernet / Wi-Fi**

```xml
<CONNECTION_TYPE>IP</CONNECTION_TYPE>
<IPADDRESS>192.168.1.100:9000</IPADDRESS>
```

Адрес — строго `A.B.C.D:порт`: DC проверяет его IPv4-регулярным выражением, и имя хоста молча превращается в пустое значение. Закрепите за терминалом адрес резервацией DHCP на роутере.

**В. PAX по USB в стандартном режиме — через мост**

```xml
<CONNECTION_TYPE>IP</CONNECTION_TYPE>
<IPADDRESS>127.0.0.1:27016</IPADDRESS>
```

На терминале включите связь с кассой по USB и перезагрузите его. Проверка: `dcctl bridge status`, затем `dcctl bridge probe`.

**Г. Bluetooth через `/dev/cu.*`**

На macOS 26 этот путь ненадёжен (подробности ниже). Для Bluetooth лучше вариант Д.

```xml
<CONNECTION_TYPE>COM</CONNECTION_TYPE>
<CONNECTION_PORT>/dev/cu.ИМЯ-ТЕРМИНАЛА</CONNECTION_PORT>
<CONNECTION_BAUDRATE>115200</CONNECTION_BAUDRATE>
<AUTO_SEARCH>OFF</AUTO_SEARCH>
<ADVANCED_AUTO_SEARCH>OFF</ADVANCED_AUTO_SEARCH>
```

Это вариант А, только порт беспроводной:

1. На терминале в настройках связи с кассой выберите **BLUETOOTH** и перезагрузите его. `PIPE` — для кассовой программы, работающей на самом терминале; `TCPIP OVER BLUETOOTH` не нужен.
2. На маке: Системные настройки → Bluetooth → терминал → «Подключить» — только для первого сопряжения.
3. После сопряжения macOS создаёт порт `/dev/cu.<имя терминала>` — найдите его через `dcctl ports` и впишите в `CONNECTION_PORT`.
4. **Отключите терминал** в Пункте управления → Bluetooth и больше не подключайте его вручную. Соединение поднимает сам DC, когда открывает порт.

Почему так. При ручном «Подключить» macOS 26 отдаёт единственный канал RFCOMM терминала своей службе дисплеев Брайля (в журнале — профиль `"Braille"`). Служба Serial Port, через которую работает `/dev/cu.*`, тот же канал открыть уже не может: `OI_RFCOMM_Connect failed (status=911)`. Порт при этом открывается, запись проходит без ошибок, но байты до терминала не доходят, и DC отвечает ошибкой 13 «Не получено подтверждение отправки команды». Хуже того, после такой неудачи мост Serial Port в `bluetoothd` перестаёт реагировать на открытие порта, пока `bluetoothd` не перезапустить.

Тот же мост ломается при **любом повторном открытии порта**, в том числе при обычном `dcctl restart`. DC закрывает порт, канал RFCOMM остаётся поднятым, и после нового открытия `bluetoothd` больше не передаёт данные ни в одну сторону. Отключение терминала в Пункте управления не помогает, помогает только перезапуск `bluetoothd`. Поэтому для варианта Г перезапускайте DC только так:

```bash
sudo dcctl stop
# если терминал подключён в Пункте управления → Bluetooth — отключите его
sudo pkill -x bluetoothd     # launchd поднимет его сам; наушники и мышь переподключатся
sleep 15                     # /dev/cu.<имя> появляется заново секунд через 12
sudo dcctl start
```

Этот же набор команд восстанавливает связь, если терминал всё же подключили вручную или DC по Bluetooth молчит. Признак ручного подключения в журнале: `log show --last 10m --predicate 'process == "bluetoothd"' | grep -E 'RFCOMM_Connect failed|"Braille" profile'`.

Отдельный режим DC `CONNECTION_TYPE=BT` с `BLUETOOTH_NAME` на маке не подходит: он реализован только для Android (см. «Механика»).

**Д. Bluetooth через мост btbridge** — рекомендуемый способ для Bluetooth

```xml
<CONNECTION_TYPE>IP</CONNECTION_TYPE>
<IPADDRESS>127.0.0.1:27017</IPADDRESS>
```

Тот же терминал, что в варианте Г, но без `/dev/cu.*` и его сбоев: мост сам открывает канал RFCOMM терминала, а DC подключается к мосту как к IP-терминалу.

1. На терминале — связь с кассой **BLUETOOTH**, как в варианте Г.
2. Сопрягите терминал с маком (Системные настройки → Bluetooth → «Подключить»), затем **отключите** его в Пункте управления. Вручную больше не подключайте: соединение мост поднимает сам на время операции.
3. `./install.sh` — найдёт сопряжённый терминал, соберёт мост и поставит его агентом launchd. Если подходящих устройств несколько: `BT_DEVICE=<адрес> ./install.sh`.
4. При первом запуске macOS спросит, разрешить ли **BTBridge** доступ к Bluetooth, — разрешите.
5. `dcctl bt probe` — тест связи с терминалом напрямую через мост, без DC. Затем впишите в `connector.xml` блок выше и перезапустите DC.

Перезапуск DC тут обычный, `sudo dcctl restart`: мост от этого не зависит. Как он устроен — в разделе «Мост btbridge».

**После любой правки** проверьте конфиг и перезапустите службу:

```bash
dcctl check              # валидность XML, дубли тегов, формат адреса, доступность терминала
sudo dcctl restart
```

Для варианта Г вместо `sudo dcctl restart` — последовательность с перезапуском `bluetoothd` выше.

Параметр `CONFIG_WATCHER` в этой схеме правки **не подхватывает**: DC следит за каталогом `/etc`, а `/etc/connector.xml` — симлинк, так что изменение настоящего файла до него не доходит.

### Основные параметры connector.xml

| Параметр | Смысл |
|---|---|
| `SERVERPORT` | порт HTTP API, по умолчанию 9015 |
| `LOG_TYPE` | подробность лога: `OFF`, `SYSTEM`, `ADVANCED`, `DEBUG`, `VERBOSE` |
| `LOG_PATH` | каталог логов; задавайте явно — `/opt/dcservice/service/log` |
| `CONNECTION_TYPE` | `COM` или `IP` |
| `CONNECTION_PORT` / `CONNECTION_BAUDRATE` | порт и скорость для `COM` |
| `IPADDRESS` | адрес терминала для `IP` |
| `IPADDRESSGUI` | куда DC шлёт диалоги кассиру (см. [API](#диалоги-с-кассиром)); без тега диалоги отключены |
| `AUTO_SEARCH`, `ADVANCED_AUTO_SEARCH` | автопоиск порта — на маке держите `OFF` |
| `WAITACK` | ожидание подтверждения пакета терминалом, секунды |
| `WAITPACKET` | ожидание ответного пакета, секунды |
| `CONNECT_TIMEOUT` | таймаут установки соединения, секунды |
| `EXCHANGE_TIMEOUT` | предельное время операции, секунды |
| `TRIPLEACK` | трижды подтверждать завершение операции терминалу |
| `HEX_STRING_FORMAT` | отдавать в HEX поля, которые нельзя передать в XML строкой |
| `RESPONS_HEX_FIELDS` | номера полей ответа, всегда отдаваемых в HEX (через `;`) |

Полный список — в руководстве вендора «DC Linux Service. Руководство программиста», разделы 2.4.1 и 4.1.

## Управление: dcctl

| Команда | |
|---|---|
| `dcctl start` / `stop` / `restart` | служба DC (`stop` ждёт реальной выгрузки из launchd) |
| `dcctl status` | состояние службы, моста, сводка конфига, проба HTTP |
| `dcctl check` | проверка `connector.xml`: XML, дубли тегов, формат адреса, доступность терминала и приёмника диалогов |
| `dcctl config` | открыть `connector.xml` в `$EDITOR` |
| `dcctl log` / `logdir` | хвост логов DC / каталог логов |
| `dcctl fg` | запустить DC в переднем плане (служба должна быть остановлена) |
| `dcctl probe [ip порт]` | проверить TCP-доступность терминала из Java (по умолчанию — адрес из конфига) |
| `dcctl ports` | последовательные порты `/dev/cu.*` |
| `dcctl jssc` | проверить, что нативная часть jssc грузится |
| `dcctl gui` | запустить DC PosGUI — окно диалогов кассира |
| `dcctl bridge start` / `stop` / `restart` | служба моста |
| `dcctl bridge status` | служба, порт, виден ли терминал на шине USB |
| `dcctl bridge probe` | проверить протокол с терминалом (мост на это время останавливается — он держит USB-интерфейс) |

| `dcctl bt start` / `stop` / `restart` | мост Bluetooth (LaunchAgent в сессии пользователя) |

| `dcctl bt probe` | тест связи с терминалом напрямую через RFCOMM (мост на это время останавливается) |

| `dcctl bt log` | поток обмена моста Bluetooth |

DC Service Control из дистрибутива (`dccontrol`) на маке не работает — он управляет службой через `systemctl`. Его заменяет `dcctl`.

## Веб-клиент: dc-client.html

Страница для работы с HTTP API вручную: собрать запрос, посмотреть его, отправить в DC и разобрать ответ. Установки не требует, внешних зависимостей нет — откройте файл в браузере.

- **Операции:** оплата, отмена, возврат, реверсал, тест связи (с банком или только с терминалом), баланс карты, сверка итогов, журнал операций, краткий и полный отчёт, копия последнего чека, загрузка ключей, произвольный запрос с любым кодом операции.
- **СБП:** оплата, запрос QR-кода, статус оплаты, возврат и статус возврата — с цепочкой кнопок «Статус этой оплаты» → «Возврат этой оплаты» → «Статус этого возврата». Статус можно опрашивать автоматически, пока приходит R01 «в обработке». Идентификаторы операций касса генерирует сама.
- **QR-код на экране терминала:** любой текст или ссылка, в том числе ссылка из ответа на запрос QR-кода СБП — кнопкой «Показать QR-кодом на терминале».
- **Поля:** обязательные отмечены звёздочкой, необязательные и любые другие поля SA — в раскрывающихся разделах. Сумма вводится в рублях и сама переводится в копейки. У каждого поля виден его номер в протоколе.
- **TerminalID** задаётся один раз в шапке. Кнопка «Узнать» спрашивает его у терминала тестом связи.
- **Запрос** виден до отправки — телом XML или JSON либо готовой командой curl.
- **Ответ:** итог (одобрено, отказ, ошибка DC с расшифровкой и подсказкой), ключевые поля, образ чека по экземплярам с копированием и печатью, все поля с названиями, обмен как есть.
- **Отмена и возврат** по кнопке из ответа на оплату: сумма, RRN и код авторизации подставляются сами.
- **«Прервать операцию»** шлёт `closeOpenConnection`, на прерванный запрос DC отвечает ошибкой 15.
- **История** запросов за сеанс. Адрес DC, TerminalID, формат и таймаут браузер запоминает; сами ответы нигде не сохраняются.

Тела запросов уходят в windows-1251. DC отвечает с `Access-Control-Allow-Origin: *`, поэтому запросы проходят прямо из `file://`. Если ваш браузер их всё же блокирует, откройте страницу через локальный сервер:

```bash
python3 -m http.server 8080 --bind 127.0.0.1     # в папке с dc-client.html
open http://127.0.0.1:8080/dc-client.html
```

Проверено в Chromium — из файла и через локальный сервер — против настоящего DC 2.0.17.7 под Linux и эмулятора терминала по протоколу SA: оплата, отмена этой оплаты, тест связи в XML и JSON, отказ, копия чека, ошибка 13, прерывание операции, недоступный DC, все три сценария СБП из DC Service Control и вывод QR-кода. В Safari и Firefox страница не проверялась.

## HTTP API DualConnector

Сжатое описание по руководству вендора («DC Linux Service. Руководство программиста», раздел 3 и приложение 6.1), проверенное на живом терминале. Коды операций и статусов сверены с перечислениями внутри `dcservice.jar`. Полное описание протокола SA — отдельный документ вендора, в дистрибутив он не входит; его выдаёт поставщик или банк.

### Точки входа

| Запрос | Что делает |
|---|---|
| `POST /` | операция на терминале. Тело — XML или JSON, ответ приходит, когда операция закончится |
| `GET /` | статус: `200` — DC сейчас обменивается с терминалом, `404` — свободен |
| `POST /command/closeOpenConnection?TerminalId=<TID>` | прервать операцию: DC шлёт терминалу EOT и закрывает соединение |
| `OPTIONS /` | preflight CORS: DC поддерживает CORS, к нему можно обращаться прямо из браузера |

`closeOpenConnection` прерывает операцию, только если DC знает терминал с этим TerminalID и с ним идёт обмен: ответ — 200 «Close exchange tid: …». Если обмена нет или операция запущена с `ipaddr` в обход конфига, DC отвечает 500 «Serve() returned a null response» и ничего не прерывает. Ответ на эту команду приходит без заголовков CORS, так что браузер его не покажет.

Разрешены методы `OPTIONS`, `GET`, `POST`, `PUT`; на остальные — ошибка 3. Разрешённые заголовки CORS: `Origin`, `X-Requested-With`, `Accept`, `X-PINGOTHER`, `Content-Type`, `Accept-Charset`.

`POST /` синхронный: соединение открыто, пока покупатель прикладывает карту и вводит PIN, — это минуты. Таймаут HTTP-клиента ставьте больше `<timeout>` в запросе. Терминал ведёт одну операцию за раз; запрос к занятому терминалу получит ошибку 16.

### Кодировка и формат ответа

| Заголовок | |
|---|---|
| `Content-Type` | `text/xml; charset=windows-1251` или `application/json; charset=windows-1251`. Без `charset` тело читается как windows-1251 |
| `Accept` | `text/xml` — ответ и ошибки в XML с HTTP 200; `application/json` — в JSON; иначе ошибки приходят HTML-страницей с HTTP 400 или 404 |
| `Accept-Charset` | кодировка ответа; по умолчанию и при неизвестном значении — windows-1251 |

Кириллица есть и в ответах: текст результата (поле 19), образ чека (поле 90). По документации другую кодировку можно задать через `charset` и `Accept-Charset`; комплект проверялся только с windows-1251.

### Запрос

XML:

```xml
<?xml version="1.0" encoding="windows-1251"?>
<request>
    <field id="0">10000</field>
    <field id="4">643</field>
    <field id="25">1</field>
    <field id="27">00199991</field>
    <timeout>180</timeout>
    <sessionID>1726912345001</sessionID>
</request>
```

JSON — тот же запрос:

```json
{
  "fields": [
    { "id": 0,  "hex": false, "value": "10000" },
    { "id": 4,  "hex": false, "value": "643" },
    { "id": 25, "hex": false, "value": "1" },
    { "id": 27, "hex": false, "value": "00199991" }
  ],
  "timeout": "180",
  "sessionID": "1726912345001"
}
```

| Элемент | |
|---|---|
| `field` | поле протокола SA: `id` — номер, значение — строка. `hex="true"` — значение передано HEX-строкой, DC превратит его в байты |
| `ipaddr` | `A.B.C.D:порт` — выполнить операцию на этом IP-терминале, а не на указанном в конфиге. Для моста — `127.0.0.1:27016` |
| `ncom`, `baudrate` | то же для терминала на последовательном порту |
| `timeout` | предельная длительность операции в секундах. Нет или `0` — ждать бесконечно. Вендор рекомендует 180 |
| `sessionID` | произвольный идентификатор операции, новый на каждую. DC помнит сессии до перезапуска; запрос с идентификатором уже закрытой сессии получит ошибку 17 |

XSD-схема из дистрибутива (`Scheme/request.xsd`) про `sessionID` не знает — при строгой валидации учтите это.

Если терминалов несколько, DC умеет выбирать параметры связи по TerminalID из запроса: секция `<DEVICES>` в `connector.xml` или отдельные файлы `/etc/<TerminalID>/Connector.xml` (руководство, п. 4.2). На маке это не проверялось.

### Ответ

Успешный обмен — набор полей в `<response>` (или `{"fields": [...]}` в JSON). Пример сокращён, значения условные:

```xml
<?xml version="1.0" encoding="windows-1251" standalone="no"?>
<response>
    <field id="0">10000</field>
    <field id="4">643</field>
    <field id="13">A1B2C3</field>
    <field id="14">000000000001</field>
    <field id="15">000</field>
    <field id="19">ОДОБРЕНО</field>
    <field id="25">1</field>
    <field id="27">00199991</field>
    <field id="39">1</field>
    <field id="90">0xDF^^...~</field>
</response>
```

Ошибка DC — вместо полей `errorcode` и `errordescription`:

```xml
<response>
    <errorcode>13</errorcode>
    <errordescription>Can't open device /192.168.1.100:9000null</errordescription>
</response>
```

```json
{ "errorcode": "13", "errordescription": "Can't open device /192.168.1.100:9000null" }
```

Отказ банка — **не ошибка DC**: он приходит обычным ответом с полями, где статус (поле 39) не равен 1.

### Коды ошибок DC

| `errorcode` | Смысл | Частая причина |
|---|---|---|
| `0` | DC не смог передать ответ терминала | внутренняя ошибка DC |
| `1` | истёк `<timeout>` запроса | покупатель не приложил карту; слишком маленький `timeout` |
| `3` | общая ошибка: параметры DC, неподдерживаемый метод HTTP, прочее | |
| `4` | ошибка поля или запроса — между кассой и DC или между DC и терминалом | битый XML или JSON, не та кодировка |
| `13` | ошибка обмена с терминалом: не открылось устройство, нет ответа, ответ не по протоколу SA | неверный адрес или порт; мост не запущен; DC запущен без `-Dos.name=Linux` (см. «Механика») |
| `15` | обмен прерван: остановка DC, `closeOpenConnection`, другой обмен | |
| `16` | устройство занято другим обменом | параллельный запрос к тому же терминалу; запрос сразу после предыдущего — DC ещё секунду-две закрывает сеанс |
| `17` | сессия с этим `sessionID` уже закрыта | повтор запроса со старым `sessionID` |

Если ответ потерян (ошибки 0, 1, 15 или обрыв HTTP), исход операции неизвестен: терминал мог успеть провести списание. Не повторяйте оплату вслепую — сначала запросите копию последнего чека (операция 63, см. ниже) и сверьте сумму и RRN.

### СБП и QR-код на экране терминала

В документации DC этих операций нет. Состав запросов взят из утилиты вендора DC Service Control (вкладка «Проверка СБП»). Работает, только если СБП подключена у банка и настроена на терминале.

| Операция | 25 | 53 | Поля, кроме 25, 27, 53 |
|---|---|---|---|
| Оплата СБП | 1 | `115` | 0, 4; 14 — идентификатор операции кассы (DC Service Control шлёт 7 случайных цифр) |
| Запрос QR-кода СБП | 1 | `116` | как у оплаты. QR-код отдаётся кассе; доступно не у всех банков |
| Статус оплаты СБП | 1 | `117` | 0, 4; **13** — тот же идентификатор кассы, что ушёл в поле 14 |
| Возврат СБП | 29 | `118` | 0, 4; 13 — идентификатор оплаты (поле 14 ответа на оплату или поле 13 ответа на статус); 14 — идентификатор возврата (32 случайные цифры) |
| Статус возврата СБП | 29 | `119` | 0, 4; 14 — поле 13 из ответа на возврат, а если его нет — отправленный идентификатор возврата |

Сценарии DC Service Control: «оплата → статус → возврат», «оплата → возврат → статус возврата» и «запрос QR-кода → статус → возврат». Результат СБП — в поле 15:

| Поле 15 | |
|---|---|
| `R00` | операция завершена успешно |
| `R01` | в обработке — запросите статус позже |
| `R10` | операция отклонена |
| `R11` | операции по QR-коду не существует |
| `R12` | не получен ответ: при 39 = 0 — на запрос статуса, при 39 = 16 — на запрос QR-кода |
| `R13` | запрос статуса не отправлен |
| `R14` | операция не добавлена в базу транзакций терминала |

**QR-код на экране терминала** — операция 41 с режимом 64 = `5`, время показа в секундах — в поле 57 (DC Service Control ставит 10). Содержимое QR-кода — в поле 86 в виде BER-TLV: тег `F6`, внутри тег `D1` с текстом в UTF-8. Поле 86 нужно передавать HEX-строкой с `hex="true"`: без этого атрибута DC отправит на терминал сами символы HEX-строки, а не байты — проверено. Результат — в поле 67: `0` — QR-код выведен, `3` — ошибка вывода. DC Service Control шлёт эту операцию без поля 27.

```xml
<request>
    <field id="25">41</field>
    <field id="57">10</field>
    <field id="64">5</field>
    <field id="86" hex="true">F63AD138D095D181D0BBD0B820D0B2D18B20D18DD182D0BE20D0B2D0B8D0B4D0B8D182D0B5202D20D0B2D181D0B520D185D0BED180D0BED188D0BE2E</field>
    <timeout>60</timeout>
    <sessionID>qr-0001</sessionID>
</request>
```

Здесь в QR-коде текст «Если вы это видите - все хорошо.» — тот же, что шлёт DC Service Control.

### Как понять, что операция прошла

Успех — **только** `39 = 1`. Остальные значения из перечисления DC:

| Поле 39 | |
|---|---|
| `0` | не определён |
| `1` | одобрено |
| `13` | аварийная отмена |
| `16` | отказано |
| `17` | одобрено офлайн |
| `34` | нет связи |
| `53` | операция прервана |

По документации вендора успешным считается только `1`. Как трактовать `17`, уточните у банка. Для кассира показывайте текст из поля 19, для разбора — код ответа хоста из поля 15.

### Образ чека: поле 90

Поле 90 — один или несколько блоков вида `0xNN^^<текст>~`: тег, два `^`, текст чека, `~` в конце. Строки внутри текста разделены символом CR; в XML он приходит как `&#13;`. Каждый блок — отдельный экземпляр чека, на практике с тегами `0xDF` и `0xDA`. Для печати уберите тег с `^^` и `~`, а CR замените переводом строки. Отступы внутри строк — часть вёрстки, их не трогайте.

`./dc-test.sh slip` разбирает поле 90 из ответа и печатает чеки по отдельности:

```bash
./dc-test.sh sale 100 | ./dc-test.sh slip
```

**Ширину чека DC не задаёт.** Поле 90 приходит от терминала уже свёрстанным — с переносами и выравниванием пробелами. Параметра ширины нет ни в `connector.xml`, ни в DC Service Control, ни в DCConsole: его ключ `-f1` только отбрасывает всё, кроме блоков `0xDF` и `0xDA`. Ширина строки настраивается в ПО терминала под ленту ККТ — обычно 32 символа для ленты 57 мм и 42–48 для 80 мм. Как и режим окон, её меняет банк или сервисная служба. Переносить строки на стороне кассы можно, но выравнивание колонок при этом поедет.

Если в тексте окажутся символы, которые нельзя передать строкой в XML, DC отдаст поле в HEX с атрибутом `hex="true"` (параметр `HEX_STRING_FORMAT`). Номера полей, которые всегда отдаются в HEX, задаёт `RESPONS_HEX_FIELDS`.

### Диалоги с кассиром

Во время операции терминал может попросить кассу показать сообщение, задать вопрос или запросить ввод. DC пересылает такие запросы по TCP на адрес из `IPADDRESSGUI`. Там слушает либо DC PosGUI вендора (`dcctl gui`, по умолчанию `127.0.0.1:6000`), либо ваше кассовое ПО. Без тега `IPADDRESSGUI` диалоги отключены.

**Окна инициирует терминал, а не DC.** DC отправляет окно, только когда терминал присылает пакет с операцией 52 — запрос кассиру. Тест связи таких пакетов не шлёт никогда, поэтому на `./dc-test.sh test` окон не будет и при исправном PosGUI. Чтобы окна шли во время операций, нужны две настройки:

| Где | Настройка |
|---|---|
| ПО терминала (UNIPOS Terminal) | «Режим отображения диалогов» = «На кассе и терминале». Меняется в меню терминала или удалённо — обычно это делает банк или сервисная служба |
| DC | «Терминальные окна на кассе» = ON в DC Service Control. В `connector.xml` это просто наличие тега `IPADDRESSGUI`: DC Service Control при OFF удаляет его |

DC при сверке итогов сообщает банку в поле 89, есть ли на кассе окна: `TW:ON`, если задан `IPADDRESSGUI`.

Проверить приёмник без терминала: `./dc-test.sh gui [1-5]`. Команда шлёт по адресу из `IPADDRESSGUI` тот же XML, что и DC, и печатает ответ. Если окно появилось и ответ пришёл, приёмник в порядке, и дальше вопрос только в том, шлёт ли терминал запросы. Проверить это можно по логу DC: при `LOG_TYPE` = `DEBUG` каждый пакет терминала пишется построчно, и запрос кассиру выглядит как строка `[25] = 52`.

Обмен — XML. DC присылает `<request>`, приёмник отвечает `<response>` с тем же `type` и закрывает соединение:

```xml
<request>
    <type>2</type>
    <data>2^6^ОПЛАТА^Подтвердите сумму 100.00</data>
    <timeout>30</timeout>
</request>
```

```xml
<response>
    <type>2</type>
    <data>2</data>
</response>
```

Запрос DC собирает из полей пакета терминала: `type` — поле 64, `data` — 76, `adata` — 77, `timeout` — 57 (по умолчанию 30 секунд). Ответ разбирается обратно в те же поля. Запрос DC шлёт в windows-1251; ответ может быть в любой кодировке, объявленной в заголовке XML, — PosGUI, например, отвечает в UTF-8. DC ждёт ответа `timeout` плюс 5 секунд.

| `type` | Окно | Запрос | Ответ `data` | Ответ `adata` |
|---|---|---|---|---|
| 1 | информация | `data`, `timeout` | `0` — сразу, без ожидания кассира | |
| 2 | подтверждение | `data`, `timeout` | код кнопки (ниже) | |
| 3 | выбор из списка | `data`, `adata` — варианты через `;` или `\n`, `timeout` | код кнопки | выбранный вариант как 2^m: первый — `1`, второй — `2`, третий — `4`… |
| 4 | ввод | `data`, `adata` — маска ввода, `timeout` | код кнопки | введённая строка |
| 5 | печать | `data` — текст для печати | по документации `0` — напечатано, `64` — ошибка | |

`data` в запросе: `уровень^кнопки^заголовок^текст`.

- **Уровень:** `1` — информация, `2` — вопрос, `3` — предупреждение, `4` — критическая ошибка. Необязателен.
- **Кнопки** — битовая маска: `0x01` OK, `0x02` Да, `0x04` Отмена, `0x08` Нет. Необязательна.
- **Заголовок** — до 40 символов, необязателен.
- **Текст** — до 950 символов, строки через `\n` или `;`. Обязателен.
- Разделители `^` обязательны, даже если элемент пуст: `1^^^УСТАНОВКА\nСОЕДИНЕНИЯ`.

Коды кнопок в ответе: `0` — ничего не нажато, `1` — OK, `2` — Да, `4` — Отмена, `8` — Нет, `16` — вышло время, `32` — окно закрыто по Esc, `64` — неверные параметры, окно не показано.

Про окно печати документация говорит, что `data` — готовые строки. DC PosGUI при этом ничего не печатает: он показывает текст в окне с кнопкой OK, требует тот же формат `уровень^кнопки^заголовок^текст`, а голый текст отвергает с кодом `64`. Если печать нужна по-настоящему, её делает ваш собственный приёмник.

Адрес приёмника можно задать для отдельного терминала в `/etc/<TerminalID>/Connector.xml`. `dcctl check` проверяет, что по адресу из `IPADDRESSGUI` кто-то слушает.

#### Настройки DC PosGUI

Файл — `/opt/dcservice/service/config/dcposgui.xml` (на него ссылается `/etc/dcposgui.xml`). PosGUI читает его только при старте, так что после правки его нужно перезапустить.

| Параметр | В дистрибутиве | |
|---|---|---|
| `listen` | `127.0.0.1:6000` | где слушать; должен совпадать с `IPADDRESSGUI` в `connector.xml` |
| `codepage` | `1251` | кодировка входящих запросов |
| `readtimeoutms` | `30` | время чтения пакета запроса, мс |
| `closeable` | `true` | показывать кнопку закрытия окна «×»; без параметра — не показывать |
| `fontsize` | `15` | размер шрифта в окне |
| `width`, `height` | `500`, `280` | размер окна в пикселях |
| `autosize` | `true` | подгонять окно под содержимое, но не больше `maxwidth` × `maxheight`; без параметра — выключено |
| `maxwidth`, `maxheight` | `500`, `280` | предел размера окна при `autosize`; без параметра — размер экрана |
| `positionX`, `positionY` | `767`, `421` | где открывать окно |

Настроек поведения — например, показывать окно всё время, пока идёт обмен с терминалом, — у PosGUI нет: он рисует только те окна, которые прислал терминал. Состояние видно по значку в строке меню.

Положение окна PosGUI запоминает сам: при закрытии окна он записывает его координаты, а при выходе через меню значка сохраняет весь конфиг в этот же файл. Поэтому правьте файл при остановленном PosGUI, иначе при выходе он перезапишет ваши правки.

**DC PosGUI на маке.** `dcctl gui` запускает его в переднем плане. В Доке появляется значок Java, в строке меню — значок PosGUI; окно открывается только на время запроса. Без системного трея PosGUI не стартует, но в строке меню macOS трей есть. Все пять типов окон проверены `./dc-test.sh gui` против PosGUI из дистрибутива под Linux.

### Примеры

curl, XML (тело перекодируется в windows-1251 и обратно):

```bash
cat > sale.xml <<'EOF'
<?xml version="1.0" encoding="windows-1251"?>
<request>
    <field id="0">100</field>
    <field id="4">643</field>
    <field id="25">1</field>
    <field id="27">00199991</field>
    <timeout>180</timeout>

iconv -f UTF-8 -t CP1251 sale.xml \
  | curl -sS --max-time 210 http://127.0.0.1:9015/ \
      -H 'Content-Type: text/xml; charset=windows-1251' \

```

Статус и прерывание:

```bash
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:9015/     # 404 — свободен, 200 — занят
curl -X POST 'http://127.0.0.1:9015/command/closeOpenConnection?TerminalId=00199991'
```

Python, JSON, только стандартная библиотека:

```python
import json, time, urllib.request

DC = "http://127.0.0.1:9015/"
TID = "00199991"

def dc_call(fields, timeout=180):
    body = {
        "fields": [{"id": k, "hex": False, "value": str(v)} for k, v in fields.items()],
        "timeout": str(timeout),
        "sessionID": str(time.time_ns()),
    }
    req = urllib.request.Request(
        DC,
        data=json.dumps(body, ensure_ascii=False).encode("cp1251"),
        headers={
            "Content-Type": "application/json; charset=windows-1251",
            "Accept": "application/json",
            "Accept-Charset": "windows-1251",
        },
    )
    with urllib.request.urlopen(req, timeout=timeout + 30) as r:
        resp = json.loads(r.read().decode("cp1251"))
    if "errorcode" in resp:
        raise RuntimeError(f"DC error {resp['errorcode']}: {resp.get('errordescription')}")
    return {int(f["id"]): f["value"] for f in resp["fields"]}

r = dc_call({0: 100, 4: 643, 25: 1, 27: TID})       # оплата 1.00 ₽
print("OK" if r.get(39) == "1" else "ОТКАЗ", r.get(19), "RRN", r.get(14))
```

## Мост paxbridge: PAX по USB

### Зачем

В «стандартном» USB-режиме терминалы PAX, включая модели на Prolin вроде D230, не притворяются последовательным портом. Они говорят собственным протоколом поверх двух bulk-эндпоинтов. На Linux этот протокол обслуживает модуль ядра `ttyPos` из драйвера PAX и отдаёт устройство как `/dev/ttyPos*`. Под macOS такого модуля нет, и терминал на шине виден, а `/dev/cu.*` не появляется.

Весь протокол, однако, укладывается в обычные USB-передачи, поэтому его можно говорить из userspace через libusb — без kext и без системного расширения. `paxbridge.py` так и делает: слушает TCP-порт, а байты протокола SA гоняет в терминал по USB. DC подключается к мосту как к обычному IP-терминалу.

```
DC Service ──TCP 127.0.0.1:27016──▶ paxbridge ──libusb, bulk IN/OUT──▶ PAX D230
```

### Протокол ttyPos

Восстановлен по исходникам модуля `ttyPos` из LinuxDriver V317.

- **Пакет:** `SeqNo:1 | ReqType:1 | Len:2 (LE) | Data[Len]`. `ReqType`: `0` WRITE, `1` READ, `2` STATUS, `3` RESET, `4` MAXDATA. `SeqNo` растёт на каждую новую команду, при повторе остаётся прежним.
- **Целостность** зависит от `bcdDevice` устройства. С `0x0300`: `Len` увеличивается на 1, в конец дописывается XOR всего пакета, XOR ответа обязан дать 0. У старых устройств 8-битная контрольная сумма раскладывается по старшим полубайтам `SeqNo` и `ReqType`.
- **Старт:** при `bcdDevice ≥ 0x0300` — vendor control-запрос «set host» (`bmRequestType 0x40`, `bRequest 0x01`, `wValue 0x0300`). При `≥ 0x0200` — запрос MAXDATA, который возвращает максимальную длину данных в пакете.
- **Обмен — опросом.** STATUS возвращает четыре `uint32`: размеры буферов терминала, сколько байт он хочет отдать (`TxLeft`) и сколько готов принять (`RxLeft`). Мост читает READ-ом, пока `TxLeft > 0`, и пишет WRITE-ом не больше `RxLeft`. В простое пауза опроса — 5 мс (`--idle-ms`).
- **Ошибки:** на сбой передачи команда повторяется с тем же `SeqNo`, до 5 раз — как в драйвере.

Известные устройства: VID `2FB8` (PAX Prolin) с PID `1101`, `110B`, `110E`, `0101` и старый `1234:0101`. Другой VID/PID можно указать явно: `--vid`/`--pid`.

### Как работает служба

- Служба `ru.inpas.paxbridge` слушает `127.0.0.1:27016` — только локальный адрес.
- USB открывается при первом подключении DC и дальше держится открытым. Пока DC не подключался, мост устройство не трогает, поэтому служба безвредна и без терминала PAX.
- На каждое подключение DC мост заново согласует протокол с терминалом. Если согласование не прошло (кабель передёргивали, терминал перезагружался), мост переоткрывает устройство и пробует ещё раз в рамках того же подключения, чтобы запрос кассы не потерялся.
- Путь к libusb прописан в plist явно: под launchd нет окружения шелла, а Homebrew на Apple Silicon ставит библиотеку в `/opt/homebrew/lib`, куда загрузчик сам не смотрит.
- Лог — `/opt/dcservice/service/log/paxbridge.log` (`dcctl bridge log`): каждое подключение и каждый блок данных в обе стороны с hex-дампом.

### Запуск вручную

```bash
cd /opt/dcservice/bridge
.venv/bin/python3 paxbridge.py --list              # USB-устройства, известные PAX помечены
.venv/bin/python3 paxbridge.py --probe             # согласовать протокол и запросить STATUS
.venv/bin/python3 paxbridge.py --serve -v          # мост в переднем плане (службу сначала остановить)
.venv/bin/python3 paxbridge.py --selftest          # проверка протокола на эмуляторе, без железа
```

| Опция | По умолчанию | |
|---|---|---|
| `--host`, `--port` | `127.0.0.1`, `27016` | где слушать |
| `--vid`, `--pid` | известные PAX | выбрать устройство по VID/PID (hex) |
| `--index` | `0` | какое по счёту, если подходящих устройств несколько |
| `--interface` | автоматически | номер USB-интерфейса; по умолчанию берётся vendor-класс с bulk IN/OUT |
| `--idle-ms` | `5` | пауза опроса в простое |
| `--libusb` | ищется сам | путь к `libusb-1.0.dylib`; то же — переменная `PAXBRIDGE_LIBUSB` |
| `-v` | | подробный лог: каждый пакет протокола |

USB-интерфейс может занять только один процесс: пока работает служба, ручные `--probe` и `--serve` получат ошибку захвата интерфейса. `dcctl bridge probe` сам останавливает службу на время проверки.

### Что проверено

- Кодирование и разбор пакетов сверены с C-кодом драйвера на 800 пакетах разной длины в обоих режимах целостности.
- `--selftest` прогоняет согласование, опрос, чтение и запись против эмулятора терминала.
- Живой D230 (`2FB8:1101`, `bcdDevice 0x0300`): maxdata 32763, буферы 10240 и 65536 байт; тест связи, оплата и отмена через DC прошли, мост работает службой launchd.

Не проверено на железе: передёргивание кабеля во время работы, сон и перезагрузка мака, модели с `bcdDevice < 0x0300`.

## Мост btbridge: Bluetooth

### Зачем

Терминал по Bluetooth macOS показывает как последовательный порт `/dev/cu.<имя>`, но этот порт — не драйвер, а мост Serial Port внутри `bluetoothd`. На macOS 26 он ломается в двух случаях:

- **ручное «Подключить».** Единственный канал RFCOMM терминала забирает служба дисплеев Брайля, а Serial Port получает `OI_RFCOMM_Connect failed (status=911)`;
- **повторное открытие порта**, в том числе `dcctl restart`. Канал остаётся поднятым, но данные через мост больше не идут.

Порт при этом открывается, запись проходит без ошибок, а до терминала не доходит ни байта. Лечится только перезапуском `bluetoothd` (подробности — в варианте Г). `btbridge.swift` обходит этот мост: открывает канал RFCOMM терминала напрямую через IOBluetooth и отдаёт его DC как TCP-порт.

### Как работает

- Слушает `127.0.0.1:27017`, клиент один. DC 2.1 подключается к мосту при старте и держит соединение, пока работает. Второе подключение вытесняет первое, только если пришлёт данные: проверки порта из `dcctl` соединение DC не рвут.
- Канал RFCOMM мост открывает, как только подключился DC, и держит его, пока DC подключён, — в том числе между операциями. Стоит канал отпустить, как macOS отдаёт его службе Брайля.
- Если канал закрыл терминал (сон, перезагрузка), мост переоткрывает его в фоне: через 2, 4, 8… до 30 с. Попытку, не завершившуюся за 12 с, снимает сторож: пока терминал недоступен, `bluetoothd` не сообщает ни успеха, ни отказа, и без сторожа мост ждал бы вечно. DC отключился — канал закрывается и свободен для других.
- Если соединение с терминалом уже поднял кто-то другой (ручное «Подключить», процесс с `/dev/cu.*`), мост рвёт его и открывает свой канал.
- **Опоздавшие кадры не доставляются.** Кадр, пришедший, пока канал открывался, уходит терминалу, только если открытие уложилось в `--ack-budget` (4 с). Иначе DC уже перестал ждать подтверждения (`WAITACK`, 5 с) и вернул кассе ошибку, а опоздавший кадр терминал бы принял и выполнил операцию, которую касса считает несостоявшейся. Такой кадр отбрасывается, в логе — строка `кадр терминалу не отправлен`.
- Номер канала мост берёт из SDP-записи Serial Port терминала.

### Доступ к Bluetooth и запуск

TCC выдаёт доступ к Bluetooth «ответственному» процессу и сверяет его `Info.plist`. Отсюда устройство моста:

- установщик собирает мост в `BTBridge.app` с `NSBluetoothAlwaysUsageDescription` и подписывает ad-hoc с идентификатором `ru.inpas.btbridge`;
- мост — LaunchAgent в сессии пользователя `RUN_USER` (`~/Library/LaunchAgents/ru.inpas.btbridge.plist`, `LimitLoadToSessionType=Aqua`). Работает, пока пользователь вошёл в систему; на кассовом маке включите автовход;
- при первом запуске macOS спрашивает, разрешить ли BTBridge доступ к Bluetooth. Разрешение привязано к подписи сборки: если бинарник изменился, установщик сбрасывает запись (`tccutil reset BluetoothAlways ru.inpas.btbridge`), и вопрос повторяется. Со старой записью TCC молча отказывает и заново не спрашивает;
- запущенный прямо из терминала, мост получил бы права терминала. Поэтому `dcctl bt probe` и `list` запускают его через `open BTBridge.app`.

### Запуск вручную

```bash
dcctl bt list                    # сопряжённые устройства и каналы Serial Port
dcctl bt probe                   # тест связи с терминалом (агент на это время останавливается)
dcctl bt log                     # поток обмена
open -n -W --stdout /dev/stdout /opt/dcservice/btbridge/BTBridge.app --args --probe --device UNIPOS --count 5
```

| Опция | По умолчанию | |
|---|---|---|
| `--serve` / `--probe` / `--list` | | мост / тест связи напрямую / сопряжённые устройства |
| `--device` | единственный сопряжённый с Serial Port | терминал: имя или адрес |
| `--channel` | из SDP | канал RFCOMM, если в SDP его нет |
| `--host`, `--port` | `127.0.0.1`, `27017` | где слушать |
| `--ack-budget` | `4` | сколько секунд можно открывать канал, пока DC ждёт подтверждения. Держите меньше `WAITACK` |
| `--count` | `1` | повторы `--probe` |
| `-v` | | подробный лог |

### Что проверено

- Живой PAX D230 по Bluetooth, DC 2.1.0.15, macOS 26.6: тест связи через DC — 15 из 15, в том числе после перезапусков DC и моста. Канал открывается за 0,7–1 с при подключении DC, операции идут без задержки.
- Перезагрузка терминала: мост увидел закрытие канала, четыре попытки снял сторож, через 2 минуты, когда терминал загрузился, канал открылся сам. Тесты связи через DC сразу после этого прошли.
- Вытеснение: после перезапуска DC соединение с терминалом держала служба macOS — мост разорвал его и открыл свой канал.
- Проверки порта (`dcctl bt status`, `dcctl check`) соединение DC не рвут.
- `--probe`: пять циклов «открыть канал → тест связи → закрыть» подряд.

Не проверено: оплата через мост, сон терминала, сон и перезагрузка мака, вход другого пользователя. Защита от опоздавших кадров добавлена после случая на ранней версии моста: канал открывался 5 с, DC уже вернул кассе ошибку, а кадр отмены всё равно ушёл терминалу.

## Механика: что мешает DC на macOS и как это обойдено

DC — Java-приложение, и формально переносимо. Но в коде есть места, где ОС определяется явно и ветки для macOS нет или она недоделана. Ниже — что именно найдено в байт-коде `dcservice.jar` 2.0.17.7 и как комплект обходит это, не трогая файлы дистрибутива.

| # | Где | Что происходит на macOS | Обход |
|---|---|---|---|
| 1 | фабрика транспорта | для macOS создаёт `null` вместо TCP-клиента и последовательного порта → `Can't open device …null`, errorcode 13 | `-Dos.name=Linux` |
| 2 | путь к конфигу | для macOS строится из переменной `CSINSTALL`, без неё — `NullPointerException` | Linux-ветка читает `/etc/connector.xml` → симлинк на конфиг в `/opt/dcservice` |
| 3 | jssc | встроенный jssc 2.9.2 и загрузчик scijava 2.3.x не знают сочетания macOS + arm64 | jssc 2.10.4 первым в classpath и его `libjssc.dylib` на `java.library.path` |
| 3а | jSerialComm (DC 2.1) | из-за `os.name=Linux` грузит Linux-сборку `.so` → запрос по COM/Bluetooth обрывается без ответа | маковская `libjSerialComm.dylib` из `dcservice.jar` на `java.library.path` |
| 4 | монитор устройств | с `os.name=Linux` выбирается Linux-монитор, `libudev` не находится | DC сам переходит на запасной вариант; на обмен не влияет |
| 5 | DC PosGUI | своя проверка ОС: Windows, Linux или «неизвестно»; для macOS папка конфига — `null`, ищется `null/dcposgui.xml` | `-Dos.name=Linux`, симлинк `/etc/dcposgui.xml`, тема Swing Metal |
| 6 | `AUTO_SEARCH` | поиск порта через `/sys` и `udevadm` | держать `OFF` |
| 7 | DC Service Control | управляет службой через `systemctl` | `dcctl` |
| 8 | режим `BT` (`BLUETOOTH_NAME`) | реализован только для Android через `android.bluetooth`; на других ОС вместо соединения получается `null` | Bluetooth через мост btbridge — вариант Д (или `/dev/cu.*` — вариант Г) |
| 9 | мост Serial Port в `bluetoothd` (macOS 26, не DC) | ручное «Подключить» отдаёт канал службе Брайля; повторное открытие `/dev/cu.*` обрывает передачу данных до перезапуска `bluetoothd` | btbridge открывает канал RFCOMM сам (вариант Д) |

### 1. Фабрика транспорта

Главная причина, по которой DC на маке не работает вообще, — даже по сети. Упрощённая реконструкция по байт-коду (не исходник вендора):

```
// карта ОС → номер ветки: WINDOWS→1, LINUX→2, ANDROID→3; MAC_OS в карте нет
createTcpClient(addr):  switch (ветка) { case 1, 2, 3: return new TcpClient(addr); default: return null }
createUsbHost(port):    switch (ветка) { case 1, 2:    return new Serial(port);    default: return null }

BufferedDevice.init():
    device = фабрика.create…(…)
    if (device == null) return false     // наружу: "Can't open device <адрес>null"
```

Тип ОС DC берёт из системного свойства `os.name` (через Apache Commons `SystemUtils`). Обёртка `bin/dcservice-run.sh` запускает JVM с `-Dos.name=Linux`, и DC идёт по рабочей Linux-ветке. Отсюда и остальная раскладка: Linux-ветка читает конфиг из `/etc`, а лог по умолчанию пишет в `/var/log/dualconnector` — установщик создаёт этот каталог с правами `RUN_USER`.

Если запустить DC штатным `dcservice.sh` или просто `java -jar dcservice.jar`, симптом вернётся. Запускайте через `dcctl` или `bin/dcservice-run.sh`.

### 2. Путь к конфигу

Для macOS DC собирает путь к конфигу из переменной окружения `CSINSTALL`, а без неё падает с `NullPointerException` при старте. После подмены `os.name` эта ветка не используется: конфиг читается из `/etc/connector.xml`. Там лежит симлинк на `/opt/dcservice/service/config/connector.xml`, так что источник правды один. `CSINSTALL` обёртка на всякий случай тоже выставляет.

Побочный эффект — `CONFIG_WATCHER`: DC следит за каталогом `/etc`, а меняется файл по ту сторону симлинка. Правки на лету не подхватываются, после них нужен `sudo dcctl restart`.

### 3. jssc и нативная библиотека

Нужен только для канала А. В `dcservice.jar` встроены jssc 2.9.2 и загрузчик нативных библиотек scijava native-lib-loader 2.3.x. Для macOS загрузчик знает только `INTEL_32`, `INTEL_64` и `PPC`, так что на arm64 отвечает «No native library available for this platform».

Обход в два шага:

1. `lib/jssc-2.10.4.jar` идёт в classpath **перед** `dcservice.jar` и перекрывает встроенные классы jssc. В 2.10.4 есть `natives/osx_arm64/libjssc.dylib`.
2. Сам загрузчик jssc не везёт — на classpath остаётся тот же старый scijava. Но `NativeLoader.loadLibrary()` сначала пробует `System.loadLibrary("jssc")` и только при неудаче идёт в распаковщик. Установщик достаёт `libjssc.dylib` в `native/`, а обёртка передаёт `-Djava.library.path=/opt/dcservice/native` — до определения архитектуры дело не доходит.

Поэтому `dcservice.jar` обязан быть в classpath и для проверки jssc (`dcctl jssc`): без него нет классов scijava, и будет `NoClassDefFoundError`.

### 3а. jSerialComm (DC 2.1)

С версии 2.1 DC открывает последовательный порт уже не через jssc, а через встроенную jSerialComm 2.10.4. jssc остаётся только в мониторинге устройств. jSerialComm выбирает нативную сборку по `os.name`, а оно подменено на `Linux`. Поэтому библиотека распаковывает `libjSerialComm.so`, и macOS отказывается её загружать: «slice is not valid mach-o file».

Ошибка `UnsatisfiedLinkError` вылетает из `Serial.init()` мимо его `catch (Exception)`, и поток HTTP-обработчика умирает. В логе после строки «Пробуем открыть порт …» больше ничего нет. Касса получает оборванное соединение без ответа: у curl это `Empty reply from server`, у браузера — `Failed to fetch`. Затрагивает каналы А и Г; каналов Б и В не касается.

Обход тот же, что для jssc. До распаковки jSerialComm пробует `System.loadLibrary("jSerialComm")`, а имя файла для этого вызова JVM строит по настоящей ОС: `libjSerialComm.dylib`. Установщик кладёт туда маковскую сборку из того же `dcservice.jar` (`OSX/aarch64/libjSerialComm.jnilib`), в `native/` рядом с `libjssc.dylib`. `dcctl jssc` проверяет загрузку обеих библиотек, jSerialComm — при `os.name=Linux`, как у службы.

### 4–5. Монитор устройств и PosGUI

С `os.name=Linux` DC выбирает Linux-монитор подключения устройств. Тот не находит `libudev` и сам переходит на запасной вариант; на проверенных сценариях это на обмен не повлияло.

У DC PosGUI своя проверка ОС, где macOS попадает в «неизвестно», а папка конфига остаётся `null`. `dcctl gui` запускает PosGUI с `-Dos.name=Linux`, и тот читает `/etc/dcposgui.xml` — симлинк на `/opt/dcservice/service/config/dcposgui.xml`. Тему Swing обёртка задаёт явно — Metal: иначе Swing, решив по `os.name`, что он на Linux, попробует GTK.

## Диагностика

Первым делом — `dcctl status` и `dcctl check`, затем лог: `dcctl log`. Для подробного лога поставьте `LOG_TYPE` = `DEBUG` или `VERBOSE` и перезапустите службу.

| Симптом | Причина и что делать |
|---|---|
| `Bootstrap failed: 5: Input/output error` | служба уже загружена или ещё выгружается. `dcctl status`, затем `sudo dcctl restart` |
| errorcode 13, `Can't open device …null` | DC запущен без `-Dos.name=Linux` — не через `dcctl` или `bin/dcservice-run.sh`. Реже: адрес в конфиге не прошёл проверку формата (`dcctl check`) |
| правка `connector.xml` не действует, операции идут на старый адрес | правки не подхватываются на лету (см. «Механика», п. 2) → `sudo dcctl restart` |
| служба не стартует, в `launchd.err.log` ошибка разбора XML | чаще всего вложенные комментарии `<!-- … <!-- … --> … -->`. `dcctl check` покажет строку |
| `AccessDeniedException` при старте | файлы в `/opt/dcservice` без прав на чтение (например, после ручного `sudo cp`) → повторите `./install.sh` |
| служба перестала стартовать после обновления IDE | DC работал на Java из IDE (`jbr` в `~/Library`), и её не стало. Поставьте системный JDK и повторите `./install.sh` |
| `NoClassDefFoundError: org/scijava/…` или `UnsatisfiedLinkError: … jssc` | нарушен classpath или нет `native/libjssc.dylib` → `dcctl jssc`, при ошибке — `./install.sh` |
| запрос по COM/Bluetooth обрывается без ответа: `Empty reply from server`, в браузере `Failed to fetch`; в логе последняя строка — «Пробуем открыть порт …» | DC 2.1 не загрузил jSerialComm: нет `native/libjSerialComm.dylib` (см. «Механика», п. 3а) → `dcctl jssc`, при ошибке — `./install.sh` |
| `No route to host` при живом терминале | проверьте маршрут: `route -n get <IP терминала>`. Если он уходит в `utun*` или локальный адрес мака `198.18.x.x`, трафик забирает VPN или прокси-клиент — добавьте локальную сеть в исключения |
| терминал подключён, а `dcctl ports` пуст | `./usb-diag.sh`. Если PAX виден на шине, а порта нет, — это канал В, нужен мост |
| по Bluetooth DC отвечает ошибкой 13 «Не получено подтверждение отправки команды», терминал молчит, хотя в настройках Bluetooth «подключён» | DC перезапускали без перезапуска `bluetoothd`, или терминал подключили вручную и канал заняла служба Брайля (см. «Подключение терминала», вариант Г). Остановите DC, отключите терминал в Пункте управления, перезапустите `bluetoothd`, запустите DC |
| вариант Д: `dcctl bt probe` или `btbridge.log` — «список сопряжённых устройств пуст» | у BTBridge нет доступа к Bluetooth: Настройки → Конфиденциальность и безопасность → Bluetooth. Если BTBridge там нет или разрешение было у прежней сборки — `tccutil reset BluetoothAlways ru.inpas.btbridge`, затем `dcctl bt restart`, и macOS спросит снова |
| вариант Д: DC отвечает ошибкой 13, в `btbridge.log` повторяется «канал RFCOMM 2 не открылся» | терминал выключен, вне зоны или связь с кассой на нём не BLUETOOTH. Мост переоткрывает канал сам, с паузами до 30 с |
| вариант Д: в `btbridge.log` — «кадр терминалу не отправлен» | канал открывался дольше `--ack-budget`, обычно в первой операции после сна терминала. Касса получила ошибку 13, терминал операцию не видел — повторите её |
| по Bluetooth нет порта `/dev/cu.<имя терминала>` или DC пишет `Can't open device` | на терминале не выбран режим BLUETOOTH, терминал вне зоны или сопряжение сброшено. Удалите терминал в настройках Bluetooth и подключите заново |
| терминал пишет «от кассы не получен terminal id» | в запросе нет поля 27 (см. «Поля») |
| окна кассира не появляются | на тесте связи их не бывает никогда. Проверьте приёмник: `./dc-test.sh gui`. Если окно есть — терминал не шлёт запросов кассиру: в UNIPOS Terminal нужен «Режим отображения диалогов» = «На кассе и терминале» (см. «Диалоги с кассиром») |
| в логе DC `Read timed out`, срабатывает `WAITACK` | терминал не отвечает по протоколу SA: на нём не включена связь с кассой, выбран другой канал или не тот порт. Для канала В — `dcctl bridge probe` |
| `dcctl bridge probe`: ошибка захвата интерфейса (`Resource busy`, `Access denied`) | интерфейс занят другим процессом — например, мостом, запущенным вручную |
| мост: «не найден libusb» | `brew install libusb`, затем `./install.sh` — путь к библиотеке пропишется в plist |
| `dcctl fg` работает, а служба по сети — нет | возможна блокировка доступа к локальной сети (Конфиденциальность и безопасность → Локальная сеть). С `LaunchDaemon` не встречалась, но исключить её нельзя |

`./usb-diag.sh` проходит по цепочке «USB-устройство → драйвер последовательного порта → `/dev/cu.*`» и говорит, на каком шаге обрыв. С `--log` добавляет системный лог USB за 5 минут.

## Ограничения

- Проект неофициальный. Проверен на DC 2.0.17.7. На 2.1.0.15 после обхода 3а по Bluetooth (вариант Г) проходит тест связи; оплата на этой версии не проверялась. DC 2.1 держит порт открытым постоянно — как он переживает сон или перезагрузку терминала, не проверялось. Обновление DC может сломать обходы из раздела «Механика».
- Вариант Г на macOS 26: повторное открытие Bluetooth-порта (в том числе `dcctl restart`) ломает мост Serial Port в `bluetoothd` до его перезапуска. Для Bluetooth используйте вариант Д.
- Мост btbridge — LaunchAgent и работает, только пока `RUN_USER` вошёл в систему. Оплата через него, сон терминала, сон и перезагрузка мака не проверялись. Первая операция после того, как терминал вернулся, может получить ошибку 13, если канал открывается дольше `--ack-budget` (после перезагрузки терминала — до 8 с); повтор проходит.
- Канал А с терминалом по USB-CDC или RS-232 не проверялся — только тот же путь по Bluetooth (Г). Маки на Intel не проверялись.
- `AUTO_SEARCH`, `ADVANCED_AUTO_SEARCH` и DC Service Control на маке не работают. Автообновление DC (`dcupdater`) не настраивалось.
- Правки `connector.xml` применяются только перезапуском службы.
- Мост обслуживает одного клиента и один терминал. Для второго терминала PAX нужен второй экземпляр моста со своими `--index` и `--port`; установщик ставит только одну службу.
- Маршрутизация нескольких терминалов по TerminalID (`<DEVICES>`, `/etc/<TerminalID>/Connector.xml`) не проверялась.
